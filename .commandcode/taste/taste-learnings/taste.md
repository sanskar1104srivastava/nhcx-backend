# Taste Learnings
- Prefers incremental validation: verify each component/API works before moving on to the next step ("first check if X works, then we can move ahead"). Confidence: 0.85
- Expects live API endpoints to be tested directly (hitting the URL) during debugging, not just inspected through code review. Confidence: 0.85
- Expects thorough, exhaustive coverage: when asked to check APIs, check every use-case/workflow, not just the first few in the list ("why you only checked till pre auth, go ahead"). Confidence: 0.9
- Prefers systematic gap analysis: check docs, identify what's missing/broken across all components, then fix and add missing pieces in a deliberate iteration. Confidence: 0.85
- Requires digging into root cause when APIs fail — research documentation, check upstream API error bodies directly, and distinguish between local code bugs vs upstream/enablement issues. Confidence: 0.85
- Expects precise, documented evidence of what worked and with what parameters, not just a "works/doesn't work" summary. Confidence: 0.9
- When asked about API flows, wants the actual upstream provider's endpoint (e.g., NHCX's real API and its curl) and full request/response/callback details shown — not just the local wrapper's abstraction. Confidence: 0.8
- Prefers deploying working changes incrementally, verifying live, and updating reports — then moving on to remaining broken items. Confidence: 0.8
- When verifying API behavior, prefers calling the deployed API Gateway endpoint (not the local dev server) and gathering results/evidence via AWS — CloudWatch logs, S3 payload buckets — using read access to AWS. Confidence: 0.8
- Script/deployment defaults must be visible and explicit in the parameter block header, not hidden behind fallback logic that fills them later — if defaults exist, show them upfront so nobody has to read the whole file to know the config. Confidence: 0.85
- Prefers architecturally separate deployment units (separate Lambdas) when distinct service roles exist (e.g., payer-side vs provider-side APIs), rather than bundling them into one Lambda. Confidence: 0.8
- When merging teammate branches, expects proactive code review of the incoming code and fixing of issues discovered (e.g., hardcoded URLs replaced with config-driven settings) rather than merging blindly. Confidence: 0.85
- Expects post-merge verification: import checks, smoke tests, and functional validation after merging branches — not just "merge complete" without proving nothing broke. Confidence: 0.85
- When testing integration flows involving multiple system roles (e.g., provider + payer), expects the agent to handle/simulate both sides end-to-end in a single test run rather than testing one side in isolation. Confidence: 0.85
- Prefers preserving existing working auth/login implementations over replacing them with new custom alternatives ("use that login method only do not create a new login method or remove for now the login"). Confidence: 0.8
- Strongly dislikes over-engineering or adding features (like auth/login) that aren't essential to the core task — wants to skip non-essential layers and get straight to the working implementation. Gets frustrated when the agent wastes time on unnecessary abstractions or offers multiple options when the path forward is obvious. Confidence: 0.85
- Expects autonomous UI verification: agent should install browser automation tools (e.g., Chrome DevTools MCP / agent-browser), start the dev server, and visually test all pages by navigating, interacting, and screenshotting — not just rely on build success. Confidence: 0.9
- Prefers traditional username/password login over raw API-key entry for admin authentication — expects a proper credential-based auth flow with session tokens rather than pasting API keys into a form. Confidence: 0.9
- Expects sensitive credentials (admin API keys) to be stored in a database (e.g., DynamoDB), not just in-memory or environment variables — wants persistent, server-side credential management. Confidence: 0.85
- Expects visibility into inbound callbacks/responses in the UI — when the system has bidirectional flows (e.g., payer→provider NHCX callbacks), wants a dedicated page or view to inspect them, not just request logs. Confidence: 0.85
